# 测斜监测管理系统

基坑测斜数据的录入、计算、预警与更正追溯系统。

- 后端：Node.js 20 + TypeScript + Fastify，计算全部在后端完成
- 存储：PostgreSQL 16
- 前端：Vue 3 + Vite + ECharts，构建后由应用服务托管（单端口）
- 测试：Vitest（纯内存仓库，无需数据库）

## 启动

```bash
docker compose up --build
# 打开 http://localhost:3000
```

首次启动应用会自动执行数据库迁移（`packages/server/src/storage/schema.sql`，幂等）。

本地开发：

```bash
npm install
npm run build:shared
docker compose up -d postgres            # 或自备 Postgres
npm run dev:server                       # http://localhost:3000
npm run dev:web                          # http://localhost:5173 （代理 /api）
npm test                                 # 后端测试
```

## 计算模型

### 测点与测段

读数按深度升序给出，深度必须为 `spacing, 2·spacing, …, depth`，等间距且与孔深相符。
第 i 个读数行（深度 d_i = i·L）对应测斜仪在该深度测得的、位于该测点与其上方测点之间的测段；
最深一行（d = 孔深）的测段底端视为**孔底固定点**（位移为 0）。

对每个深度：

- `tilt_i = (正测 − 反测) · factor`（factor 取该深度正/反测所用探头在测量时刻生效系数的均值）
- 段水平偏移 `s_i = tilt_i · L`（小角近似，正弦值即水平偏移/段长）
- 从孔底固定点往上逐段累加：测点 i 的原始累计 `C_i = Σ_{j≥i} s_j`
- 相对本基准段初始测量：`R_i(m) = C_i(m) − C_i(base)`
- 位移单位 mm，深度单位 m，速率单位 mm/d

小算例验证（测试 `engine.test.ts`）：三个测段（L=0.5 m）从孔底往上相对初始的
倾斜正弦为 0、0.004、0.002 时，三个测段顶端的累计位移依次为 0、2 mm、3 mm。

物理对称性（同一测试文件）：

- 读数与初始测量完全相同 → 相对位移处处为 0
- 探头系数翻倍、读数不变 → 位移翻倍
- 正/反测读数互换 → 位移变号

### 校核和与可疑点

`checksum_i = 正测_i + 反测_i`。理想情况下同一根管子各深度的和近似常数。
以同孔全部深度的**中位数**作为该常数的稳健估计，以 MAD 估计离散度：

```
可疑 ⇔ |checksum_i − median| > checksumTolerance + 3 · 1.4826 · MAD
```

可疑点**只标记、不自动剔除**，在测量详情页黄底标出。MAD 为 0 时退化为固定容差，
干净数据不会误报；单个离群点可被检出。

### 速率与预警分级

相邻两次测量（按时间排序）之间：

```
rate_i = (位移_i(本次) − 位移_i(上次)) / (两次测量间隔天数)
```

孔可按深度配置蓝/黄/红阈值（mm/d），代表深度之间线性插值，两端取边界值；
每一行必须 蓝 < 黄 < 红（录入时拒收非递增）。各深度按 `|rate|` 定级，
一次测量的等级取所有深度的最高等级。同孔测量时刻必须唯一。

定级为**严格超过**阈值（等于阈值不预警），并带 1e-9 mm/d 的浮点容差：
读数经“倾斜 → 段偏移 → 累计 → 速率”几步浮点运算后，名义上恰好等于阈值的
速率可能算成 1.0000000000000009 之类，容差吸收该噪声，避免临界误报。

## 基准（datum）——关键设计决策

以下三种事件产生**新的基准段**，在上传时显式标记：

1. 测斜管受损修复（`tube_repair`）
2. 更换探头（`probe_change`）
3. 正式重设初始测量（`manual_reset`）

孔的第一次测量自动成为第 0 段基准。每段内部，相对剖面 = 本次原始累计 − 段内第一次测量的原始累计。

### 跨段如何接起来：**复测当天逐深度冻结（每个深度各有一个拼接锚点）**

设新段 k 的第一次测量为 `reset_k`（修复/换探头当天的复测），上一段 k−1 的最后一次测量为 `last_{k−1}`。
这两次测量紧邻，而新旧探头（或修复前后的管子）在每个深度都可能存在零漂，**单靠这一对测量无法区分
逐深度差异里多少是系统零漂、多少是这段间隔内的真实位移**。本系统就此拍板：**按零真实位移处理**——
复测当天的连接剖面在每个深度都强制等于旧段末测的连接剖面，即逐深度锚点：

```
anchor_k[d] = connected(last_{k−1}, d) = anchor_{k−1}[d] + R_d(last_{k−1})
connected(m, d) = anchor_{group(m)}[d] + R_d(m)
```

效果（以本仓库的复现场景为准：2 m 孔、0.5 m 间距、旧探头末测 [4,2,0,0]，
新探头每段带 0.002 常数零漂）：

- 换探头复测当天：段内相对剖面处处为 0，**连接剖面仍是 [4,2,0,0]，孔底固定点保持 0**；
  跨基准首条速率**严格为 0**（直接拷贝旧末测剖面，连浮点残差都没有），**不触发预警**。
- 之后一次测量（浅部两段各再增 2 mm / 1 mm）：连接剖面 [6,3,0,0]，
  速率 [1,0.5,0,0] mm/d，与换探头之前的曲线在叠加图上首尾相接。

剖面图上用**红色虚线**标出每个基准切换位置，并悬浮显示段号、切换日期；
跨基准的首条速率逐点打 `crossDatum` 标记（值恒为 0），提醒这是按“零位移”假设对齐出来的，
不是实测变化。实现见 `engine/compute.ts`（`buildAnchorsAndConnected`）。

### 为什么选这个方案，代价是什么

把“复测↔旧末测”的差异记到谁的账上，有三种合理做法：

- **方案 A：逐深度对齐（本系统采用）。** 假设该间隔内无真实位移，差异**逐深度**全部视为系统差。
  无论零漂是整孔常数、随深度线性还是任意形状（注意：每段倾斜上的常数零漂，沿孔累加后在剖面上
  是阶梯形，不是常数），都被锚点向量整体吸收；孔底固定点在连接坐标系下永远保持 0；复测当天
  速率恒为 0，不会误报。
- **方案 B：逐深度差异取中位数，作为一个标量偏移（旧实现，已废弃）。** 只在“零漂在剖面上近似
  整孔常数”时成立。常数零漂累加出的阶梯差（上例 [0,1,2,1]）中位数只对齐了一个深度，孔底固定点
  被抬成非零，复测当天出现 [-1.5,-0.5,0.5,0.5] mm/d 的虚假速率、误挂蓝预警，之后整条曲线错位，
  叠加图与历史接不上——这正是本次修复的故障。
- **方案 C：不对齐，新段从 0 重新开始。** 叠加图在每次换探头处断开，长历时变形无法连续判读；
  只有显式关闭“跨基准拼接”查看段内相对剖面时才有意义（前端“跨基准拼接位移”开关）。

方案 A 的代价（明确告知使用者）：

1. **复测与旧末测之间若确有真实变形，该变形会被整体吃掉一次**（逐深度吃掉，而不仅是一个标量）。
   这是“分不清零漂与位移”时的保守选择：宁可少报一次间隔的变形，也不让换探头制造假预警；
   该间隔之后的速率不受影响。跨基准首条速率恒打 `crossDatum` 标记，判读时可人工甄别。
2. **旧段末测剖面上的局部形状（真实变形形状、坏点）会原样带进新段**。若旧末测本身有误，
   更正该次测量后整孔重算，冻结过去的锚点和之后各次的连接剖面都会随之更新（见下节），
   错误不会永久锁死；可疑点仍按校核和规则照常标记。
3. 连接坐标系的绝对含义是“相对第 0 段初始测量、并在每次基准切换处不断裂”的连续位移，
   而不是每次复测都重新归零。段内相对剖面（`relativeDisplacements`）始终独立提供，
   需要“本次相对新探头基准”的口径时直接看它。

对 `tube_repair`（修管）与 `manual_reset`（正式重设初始）同样适用逐深度冻结：
显式重设基准意味着“从此刻接续”，接续点前后判为同一条连续曲线；若希望重设后从 0 开始、
不与历史接续，在叠加图上取消“跨基准拼接位移”即可查看各段独立剖面。

## 更正、版本与历史判级

- **测量与标定都是版本化实体**，更正走乐观并发控制（CAS）：
  `UPDATE … WHERE revision = baseRevision`。两人同时基于同一版本更正时，一笔成功、
  另一笔得到 409 冲突提示，绝不静默覆盖；失败者取新版本后可重试。
- 每次计算结果以**内容指纹**（与测量修订号、计算时间无关的曲线/速率/等级序列化哈希）
  存入 `computed_snapshots`；内容不变不新增行。
- 因此系统可同时回答：
  - “按当时数据，这次判几级”——取 `computed_at ≤ asOf` 的最后一个快照；
  - “按现在数据应该判几级”——取最新快照。
  - 两者不同时，测量详情页并排展示并高亮差异（`GET /api/measurements/:id/history?asOf=…`）。
- **补录**一次测量到已有两次之间：测量按时间重新分段（补录点若落在某次基准复测之前，
  该基准的冻结对象自动改为补录后的旧段新末测），所有受影响的相邻测量对的速率按新时间顺序
  重算，受影响结果写新快照，旧快照保留。
- **连续多次基准切换**（包括某个新基准段里只有复测一次就又换探头/修管）：每次切换都冻结在
  当时旧段的最后一次测量上；连续两次复测的连接剖面相同，中间段的锚点等于前一段锚点。
- **更正测量或标定**：
  - 测量读数/时间/探头/基准标记变更 → 该孔重算，锚点与速率沿时间顺序级联，
    基准复测之后的连接剖面整体跟随；
  - 标定新增（含补录早期生效版本）或更正 → 所有使用该探头的孔重算。

### 增量 ≡ 全量（硬性不变量）

`engine/compute.ts` 的增量路径实现为：**全量重算 + 逐结果指纹比对**——
输入指纹（读数、时间、基准标记、在测量时刻生效的标定系数）未变的结果标记 `unchanged` 复用，
只对变化结果写快照；服务层在每次重算时都额外断言增量结果与全量结果序列化相等，
不一致直接抛错（`monitorService.recomputeBorehole`）。测试
“更正后增量结果与全量重算完全一致”验证：更正后强制全量重算不再产生任何新快照，
且服务内断言通过。

## 拒收的输入（422，带具体字段）

- 深度序列不等间距、不在 spacing 网格上或与孔深不符；同一深度出现两次
- 正测/反测读数不是有限数（NaN/Infinity 拒绝）
- 测量日期早于该孔初始测量；同孔测量时刻重复
- 探头编号没有登记（含逐行覆盖的探头）
- 阈值不是严格递增（蓝 < 黄 < 红）
- 标定系数非正；时间无法解析；缺字段

## 测试

- 三测段 0/2/3 mm 算例；首次测量相对位移为 0
- 读数相同位移处处为零；系数翻倍位移翻倍；正反测互换位移变号

- 历史判级可查，蓝 → 红的当时/现在差异
- 全部五类拒收输入及具体字段
- 换探头逐深度冻结拼接：复测当天 [4,2,0,0]/孔底为零/速率严格为零/不预警、
